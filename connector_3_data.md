# Требования к владельцам источников данных для подключения к OpenMetadata

## Цель документа

Этот документ описывает, что именно команда OpenMetadata запрашивает у **владельца каждого подключаемого источника** (базы данных, бакета, Airflow, Superset) перед и во время настройки коннектора.

Цель — получить от владельца ресурса **минимально достаточный** набор бизнес- и технической информации: чтобы коннектор настраивался с первого раза, без циклов уточняющих вопросов, и при этом каталог не «зарастал» служебной технической информацией, которая никому не нужна и только затрудняет поиск и понимание данных бизнес-пользователями.

Документ применим к каждому из четырёх типов источников, подключаемых на проде: базы данных, объектные хранилища (бакеты), Airflow, Superset BI.

## Общие принципы сбора данных

- **Один владелец — один ответ.** У каждого источника должен быть один назначенный владелец (Data Owner), который согласовывает содержимое анкеты и несёт ответственность за актуальность присланных данных.
- **Бизнес-контекст обязателен, техника — по минимуму.** Мы не просим полную техническую документацию системы (схемы БД целиком, дампы конфигов, списки всех пользователей и т.п.) — только то, что нужно для настройки конкретного коннектора и для того, чтобы каталог был понятен бизнес-пользователям.
- **Не запрашиваем секреты в анкете.** Пароли, ключи доступа, токены передаются отдельным защищённым каналом, никогда в теле анкеты или почте.
- **Данные владельца — не техническая свалка.** Поле, не обязательное для конкретного типа источника, не заполняется «на всякий случай» — это прямой урок демо-этапа: лишние детали (полные списки колонок, служебные схемы, тестовые таблицы) не добавляют ценности каталогу, а только увеличивают шум при поиске и путают пользователей.
- **Актуализация — обязанность владельца.** При изменении состава данных, структуры или ответственных владелец владелец обязан уведомить команду OpenMetadata (см. раздел «Процесс и сроки»).

## Требования к владельцам баз данных

### Бизнес-данные (чтобы каталог был понятен)

- Название БД и краткое описание назначения «человеческим языком» (например: «Биллинг — биллинговые данные по клиентам»).
- ФИО и контакт владельца (Data Owner) и, если отличается, технического контакта (DBA).
- Краткое описание ключевых схем/таблиц (не всех, а тех, что действительно представляют ценность для каталога) — 1–2 предложения на схему, не построчный data dictionary.
- Классификация чувствительности данных (если в организации принята — публичные/внутренние/конфиденциальные/персональные данные — без детализации до уровня конкретных полей).

### Технические данные (только для настройки коннектора)

- Тип БД и версия (PostgreSQL 15, MySQL 8 и т.п.).
- Host/DNS-имя и порт в **внутренней** сети (не публичный IP — прямая причина таймаутов на демостенде).
- Название базы/схем, к которым нужен доступ.
- Подтверждение, что создана выделенная **read-only** сервисная учётка (логин/пароль передаются отдельно, вне анкеты) с правами SELECT на согласованные схемы — **без изменения существующих ролей/RLS-политик**.
- Подтверждение, включено ли логирование запросов (`pg_stat_statements`, `system.query_log` или аналог) — от этого зависит, будет ли автоматически строиться lineage.
- Требуется ли TLS для подключения к БД (если да — сертификат/CA, без приватных ключей в анкете).

**Не нужно:** полный DDL/дамп 0432сей схемы, список всех существующих пользователей/ролей БД, внутренние регламенты/runbookи администрирования.

## Требования к владельцам объектных хранилищ (бакетов)

### Бизнес-данные

- Назначение бакета одной фразой (например: «ежедневные отчёты по продажам»).
- Владелец и контакт.
- Какие папки/префиксы внутри бакета содержат структурированные данные, а не служебные/временные файлы (чтобы не каталогизировать мусор).
- Классификация чувствительности данных в бакете (если принята в организации).

### Технические данные

- Тип хранилища (MinIO / S3-совместимое / другое) и внутренний endpoint.
- Имя бакета.
- Способ аутентификации хранилища (внутренний IAM или LDAP identity provider — важно знать заранее: в режиме LDAP стандартное создание пользователя через IAM API не работает).
- Подтверждение, что создана сервисная учётка с правами read-only, включая `ListBucket` (без него ингест файлов внутри бакета падает).
- Формат файлов внутри каждого структурированного префикса (JSON/CSV/Parquet и т.п.) — нужно для манифеста `openmetadata.json`.
- Согласие, что мы разместим в корне бакета манифест-файл `openmetadata.json` (технический артефакт, не влияет на бизнес-данные).

**Не нужно:** полный листинг содержимого всех бакетов, копии самих файлов/данных, мастер-ключи доступа ко всему хранилищу.

## Требования к владельцам Airflow

### Бизнес-данные

- Краткое описание назначения инстанса Airflow (какие бизнес-процессы он обслуживает).
- Владелец и контакт.
- Список приоритетных DAG (если их много) с коротким описанием, что они делают — чтобы команда каталога знала, где строить lineage в первую очередь.

### Технические данные

- Внутренний URL/DNS Airflow REST API и версия Airflow (2.x/3.x — влияет на совместимость коннектора).
- Подтверждение создания read-only сервисного пользователя/API-токена с доступом к Metadata API (список DAG, task instances) — без прав запуска/изменения DAG.
- Есть ли в ключевых DAG инструментация `inlets`/`outlets` или OpenLineage — от этого зависит, будет ли lineage автоматическим или потребуется ручное построение.

**Не нужно:** полный исходный код всех DAG, доступ на запуск/изменение пайплайнов, доступ к serving-серверу Airflow веб-интерфейса для администрирования.

## Требования к владельцам Superset BI

### Бизнес-данные

- Назначение инстанса Superset (какая бизнес-область/команда им пользуется).
- Владелец и контакт.
- Список приоритетных дашбордов (если их много) с кратким описанием бизнес-цели.

### Технические данные

- Внутренний URL/DNS инстанса Superset и его версия.
- Подтверждение создания read-only сервисной роли/API-токена с доступом к списку дашбордов/чартов/датасетов.

**Не нужно:** доступ на редактирование дашбордов, списки всех пользователей Superset, внутреннюю конфигурацию сервера.

## Что НЕ нужно передавать

Сводный античек-лист — чтобы владельцы источников не перестраховывались и не присылали «всё подряд».

- **Секреты в любом виде:** пароли, access/secret ключи, токены, сертификаты — только через защищённый канал, никогда в анкете/письме/тикете.
- **Полная техническая документация системы целиком:** полные DDL-скрипты, архитектурные схемы всей системы, внутренние runbookи эксплуатации.
- **Списки всех пользователей/ролей исходной системы** — нас интересует только выделенная сервисная учётка для коннектора.
- **Сами данные/выгрузки/дампы** — OpenMetadata не хранит и не копирует сами данные, только метаданные о них — передача выгрузок/образцов данных не требуется.
- **Полный перечень всех объектов системы, включая технические/служебные таблицы, staging/tmp-объекты, тестовые схемы** — владелец сам отбирает только то, что имеет ценность для каталога; остальное коннектор увидит сам при ingestion, но без описаний и классификации это просто шум.
- **Права шире, чем нужно:** запрос админских/записывающих прав «на всякий случай» вместо read-only — отклоняется всегда, даже если так проще настроить.

## Сводный чек-лист (анкета владельца источника)

Краткая форма, которую можно отправить каждому владельцу источника отдельно (заполняется за 5–10 минут).

| # | Пункт | Тип | Комментарий |
| --- | --- | --- | --- |
| 1 | Название источника (бизнес-название) | Бизнес | Одной фразой, понятно бизнес-пользователю |
| 2 | Владелец (Data Owner) — ФИО, контакт | Бизнес | Единственный ответственный |
| 3 | Технический контакт (если отличается от владельца) | Бизнес | DBA / администратор системы |
| 4 | Краткое описание ключевых сущностей (таблиц/бакетов/DAG/дашбордов) | Бизнес | 1–2 предложения на каждую |
| 5 | Классификация чувствительности данных | Бизнес | Публичные/внутренние/конфиденциальные/персональные |
| 6 | Тип источника и версия ПО (БД/хранилище/Airflow/Superset) | Техника | Например PostgreSQL 15, MinIO, Airflow 3.x |
| 7 | Внутренний host/DNS и порт | Техника | Только private IP/DNS, не публичный |
| 8 | Создана выделенная read-only сервисная учётка | Техника | Да/Нет — если нет, назначить срок |
| 9 | Канал передачи секретов (не в анкете!) | Техника | Секрет-менеджер / зашифрованное сообщение |
| 10 | Специфично для типа источника (query-логирование / ListBucket / OpenLineage и т.п., см. выше) | Техника | См. соответствующий раздел выше |

Заполненная анкета возвращается команде OpenMetadata, которая согласует с владельцем дату подключения.

## Процесс и сроки взаимодействия

1. **Запрос.** Команда OpenMetadata направляет владельцу источника сводный чек-лист (см. выше) и соответствующий раздел по типу источника.
2. **Срок ответа:** 3 рабочих дня на заполнение анкеты. Секреты (пароль/ключи сервисной учётки) передаются отдельно, по защищённому каналу, в течение 1 рабочего дня после согласования анкеты.
3. **Проверка связности.** Команда OpenMetadata самостоятельно проверяет доступность источника по внутреннему IP/DNS до настройки коннектора, чтобы не тратить время владельца на повторные запросы из-за сетевых проблем.
4. **Настройка коннектора и пробная ingestion.** При ошибках доступа команда OpenMetadata возвращается к владельцу точечным вопросом (например, недостающее право `ListBucket`), а не повторным запросом всей анкеты.
5. **Подтверждение.** После успешного ingestion команда OpenMetadata кратко подтверждает владельцу, что источник успешно подключён, без дальнейших действий с его стороны.
6. **Актуализация.** Владелец уведомляет команду OpenMetadata заранее (по возможности) об изменении схемы/структуры/ответственного лица — это позволяет обновить коннектор без сбоев ингеста.
