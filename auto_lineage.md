# Автоматический lineage в OpenMetadata: что настроить, чтобы не строить граф вручную

## Цель документа

На демостенде мы собирали граф lineage `sales` (Postgres) → `daily_sales_report` (Airflow) → `reports/sales_by_region.json` (MinIO) → метрика «Ежедневные продажи по регионам» — и все рёбра между Airflow, S3 и метрикой пришлось тянуть вручную через Edit Lineage в UI. Это работает на одном пайплайне, но не масштабируется на прод с десятками DAG, десятками бакетов и 50 метриками.

Этот документ — практическая инструкция: какие настройки на стороне источников и самого OpenMetadata нужно проверить/включить ЗАРАНЕЕ, чтобы lineage строился автоматически и не требовал ручного вмешательства команды.

## Когда lineage строится автоматически

OpenMetadata умеет сам строить lineage только в четырёх случаях. Всё, что выходит за их рамки, придётся достраивать вручную — как на демостенде.

| Источник автоматизации | Связь, которую строит | Обязательное условие |
| --- | --- | --- |
| Query-based lineage (логи запросов) | таблица → таблица (SQL-к-SQL) внутри одной или нескольких баз | включено query-логирование (`pg_stat_statements`, `system.query_log` и т.п.) |
| OpenLineage / `inlets`–`outlets` | пайплайн (Airflow/Spark и т.п.) → таблица/файл | инструментирование кода DAG |
| dbt manifest | модели dbt → таблицы | ингест `manifest.json`/`catalog.json` в OpenMetadata |
| Парсинг SQL BI-дашбордов | дашборд/чарт → таблица | включён Dashboard/Lineage ingestion у BI-коннектора |

**Всё остальное** — например, связь «Airflow → объектное хранилище без inlets/outlets», или связь метрики с таблицами/дашбордами — **не автоматизировано никак в принципе** и требует ручного построения через Edit Lineage, как на демостенде. Следующие разделы — конкретные настройки для каждого автоматического механизма.

## Базы данных: query-based lineage

На демостенде это единственный вид lineage, который уже работает полностью автоматически (через `GetQueries`). На каждой из 4 баз проверить:

- **PostgreSQL:** расширение `pg_stat_statements` включено в `shared_preload_libraries`, и у сервисной учётки OpenMetadata есть право на `pg_read_all_stats` (или аналог).
- **ClickHouse:** `system.query_log` включён (параметр `log_queries=1`), и ретеншн таблицы достаточный для охвата ingestion (по умолчанию 7–14 дней — сверить с частотой lineage-ingestion).
- **MySQL/иные:** аналогичный механизм (`general_log`/`performance_schema` или специфичный для OpenMetadata-коннектора) — уточнить по документации конкретного коннектора.
- Для всех 4 БД включить в OpenMetadata отдельный workflow **Lineage Ingestion** (не только Metadata) с расписанием — он использует исторические запросы, а не текущий снимок.
- **Проверка перед завершением подключения:** выполнить тестовый INSERT/SELECT между двумя таблицами и убедиться, что ребро запроса появилась в логе до того, как уверять, что связь подтянется автоматически.

## Airflow: автоматический lineage вместо ручного

Самая больная точка демостенда: `daily_sales_report` ничего не «рассказывал» OpenMetadata, что он читает из `sales` и пишет в `reports/sales_by_region.json` — граф собрали руками. Для 3 прод-инстансов это не масштабируется, поэтому обязательно:

1. **Приоритет: OpenLineage-интеграция.** Подключить провайдер `apache-airflow-providers-openlineage` ко всем 3 инстансам Airflow и настроить `OPENLINEAGE_URL`/`OPENLINEAGE_API_KEY` на ваш OpenMetadata (поддерживает приём OpenLineage-событий). При этом большинство standard-операторов (SQL, S3, GCS и т.п.) автоматически отдаёт свои input/output без изменения кода DAG.
2. **Фоллбек: явные `inlets`/`outlets`.** Где OpenLineage не покрывает оператор (кастомный PythonOperator, как в `daily_sales_report`) — явно указывать `inlets=[Table(...)]` и `outlets=[Table(...)]` в декораторе таска.
3. **Новые DAG — с инструментацией с первого дня.** Добавить пункт «inlets/outlets или OpenLineage-соватимые операторы обязательны» в code review checklist для новых DAG — дешевле сделать сразу, чем достраивать вручную потом.
4. **Старые DAG — инвентаризация.** Составить список существующих DAG во всех 3 инстансах, отсортировать по бизнес-критичности и добавить inlets/outlets только в приоритетные — остальные достраиваются вручную точечно, без погони полным охватом сразу.
5. **Убедиться, что Airflow-коннектор настроен на приём lineage-событий**, а не только на metadata ingestion (в UI связи могут не появиться даже при корректной инструментации DAG, если приём не включён).

## Superset BI: автоматический lineage через парсинг SQL

На демостенде Superset не был подключен, но на проде с 4 инстансами это один из наиболее важных источников автоматического lineage, так как он не требует изменения кода на стороне BI.

- Включить в Dashboard Service коннекторе отдельный workflow **Lineage Ingestion** (не только Metadata) — он разбирает SQL датасетов/виртуальных таблиц дашбордов и связывает с источниками.
- Связь дашборда с источниковыми таблицами найдётся, **только если эти таблицы уже закаталогизированы** через соответствующий Database Service — поэтому порядок в дорожной карте важен: все 4 БД подключаются раньше 4 инстансов Superset.
- Физические таблицы (physical), а не только virtual dataset с кастомным SQL — для custom SQL парсер работает хуже (сложные CTE/подзапросы могут не распознаться) — где возможно, предпочитать прямые табличные источники дашборда.
- После ингеста выборочно сверить 2–3 дашборда в UI — чтобы убедиться, что связи реально резолвится в правильные таблицы, а не остаются пустыми.

## Объектные хранилища (S3/MinIO): честное ограничение

Здесь важно трезво оценить границы возможного: у объектного хранилища нет собственного “query log”, поэтому связь «что записало файл в бакет» автоматически строится **только через OpenLineage/`outlets` на стороне Airflow** (см. раздел выше) — сам коннектор хранилища этого не даёт.

Что всё же можно автоматизировать для бакетов:

- Убедиться, что в каждом бакете со структурированными данными есть манифест `openmetadata.json` — без него файлы внутри вообще не появятся в каталоге — и любой lineage к ним будет невозможен.
- Сервисная учётка имеет `s3:ListBucket` (иначе ingestion тихо падает, а результат выглядит как «подключено, но пусто»).
- В ключевых DAG, которые пишут в бакеты, указан `outlets` на контейнер/объект в OpenMetadata — это единственный способ избежать ручного рисования стрелок в Edit Lineage для всех 20 бакетов.

**Честно:** если файл попадает в бакет не через Airflow/dbt/другой инструментированный пайплайн (например, вручная выгрузка), lineage к нему **неизбежно останется ручным** — это структурное ограничение OpenMetadata, а не недосмотр в настройках.

## dbt (если используется)

На демостенде dbt не использовался, но если на проде трансформации в базах данных ведутся через dbt — это самый надёжный источник автоматического lineage внутри БД, так как dbt уже знает полный граф зависимостей между моделями.

- После `dbt run`/`dbt docs generate` загружать `manifest.json` и `catalog.json` в OpenMetadata (через dbt-ingestion workflow в соответствующем Database Service).
- Связать этот шаг с CI/CD dbt-проекта (автоматическая выгрузка манифеста после каждого деплоя), а не делать вручную одноразовую загрузку.
- Если dbt не используется и не планируется — этот раздел можно пропустить, но стоит держать в виду как опцию на будущее, если часть трансформаций сейчас делается вручным SQL/скриптами и будет перенесена в dbt.

## Чек-лист перед подключением каждого источника

Пройти по этим пунктам **до** настройки коннектора — это дешевле, чем обнаруживать отсутствие lineage постфактум и достраивать вручную.

| # | Проверка | Для каких источников |
| --- | --- | --- |
| 1 | Query-логирование включено и сервисная учётка имеет право его читать | Все 4 БД |
| 2 | Отдельный workflow Lineage Ingestion включён (не только Metadata) | БД, Superset |
| 3 | Провайдер `apache-airflow-providers-openlineage` установлен и `OPENLINEAGE_URL` настроен | Все 3 Airflow |
| 4 | В custom-операторах ключевых DAG явно указаны `inlets`/`outlets` | Все 3 Airflow |
| 5 | Манифест `openmetadata.json` лежит в корне каждого бакета со структурированными данными | Все 20 бакетов |
| 6 | Сервисная учётка имеет `s3:ListBucket` | Все 20 бакетов |
| 7 | Дашборды строятся на физических таблицах, а не только virtual dataset с кастомным SQL | Все 4 Superset |
| 8 | Источники-таблицы дашборда уже закаталогизированы (Database Service настроен раньше Dashboard Service) | Порядок фаз |
| 9 | Если есть dbt — загрузка manifest/catalog встроена в CI/CD | dbt-проекты |
| 10 | По каждому новому DAG в code review есть пункт про inlets/outlets | Все 3 Airflow (процесс) |

После первого ingestion — открыть Lineage у 2–3 случайных объектов и убедиться, что связи появились без ручного вмешательства.

## Если автоматический lineage всё же невозможен

В некоторых случаях (легаси-системы без API, внешние источники без инструментации, как на демостенде) ручное построение неизбежно. Как это минимизировать:

- **Приоритизация.** Строить вручную только для бизнес-критичных потоков (например, те, на которых завязаны из 50 метрик), а не для всего.
- **Закрепить владельца.** За каждым вручным ребром закрепить владельца и дату пересмотра (в описании связи в UI или в отдельном реестре) — ручные связи не обновляются сами при изменении пайплайна.
- **Периодически переоценивать.** Раз в квартал проверять, не появилась ли у источника возможность автоматизации (новая версия Airflow-провайдера, появилась поддержка OpenLineage у нового типа источника и т.п.) — и переводить ручные связи в автоматические по мере появления такой возможности.
- **Фиксировать в governance-реестре.** Вести отдельный список всех вручных связей с причиной, почему не автоматизировано — чтобы новые члены команды не тратили время на выяснение, почему связь не появилась сама.

Итог: цель — не «ноль ручных связей любой ценой», а **предсказуемость**: команда должна заранее знать, где граф соберётся сам, а где требует ручного внимания при каждом изменении пайплайна.
